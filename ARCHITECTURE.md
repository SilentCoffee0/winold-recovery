# WinOld Recovery — Architecture (v0.1)

This document fixes the technical stack, the process model, the data model, and the module boundaries. It is the contract the implementer builds against. Where a choice deviates from the original hypothesis (C# / .NET 10 / WPF / single EXE / SQLite / Robocopy), the reason is stated.

---

## 1. Stack decision

| Concern | Decision | Alternatives considered | Why |
|---|---|---|---|
| Language / runtime | **C# 14 on .NET 10 (LTS)** | Rust + Tauri, Electron, C++ | Best Windows API reach with managed safety; one language for UI, engine, and tests; long support window. Electron/Tauri add a web runtime, a second language, and awkward elevation. |
| UI framework | **WPF** (Fluent theme, `ThemeMode=System`) | WinUI 3, Avalonia, WinForms | WPF: mature, works elevated without friction, single-file self-contained publish is supported, first-class Win32 interop, no packaging requirement. WinUI 3 has known friction running as administrator and with unpackaged single-file publishing. Avalonia is a good second choice (trimmable, smaller EXE) but adds a non-native tree/list stack and its own bugs; not needed for a Windows-only tool. WinForms would work but reads as dated and has weaker data-binding for the card UI. |
| Distribution | **Portable, self-contained, single-file EXE, x64** (`WinOldRecovery.exe`, ~70 MB compressed) plus a separate ARM64 build | Framework-dependent | A recovery tool must run on a freshly installed Windows with no runtime installed. WPF cannot be trimmed, so the EXE is large; that is acceptable. `IncludeNativeLibrariesForSelfExtract=true` (needed for the SQLite native library), `EnableCompressionInSingleFile=true`. |
| Elevation | **`requestedExecutionLevel=requireAdministrator`** in the app manifest, `SeBackupPrivilege`/`SeRestorePrivilege` enabled at startup | Run unelevated and elevate a helper | Reading other users' folders in Windows.old and deleting it later both need admin. A split-process design doubles complexity for no v0.1 benefit. |
| State store | **SQLite** via `Microsoft.Data.Sqlite` + `SQLitePCLRaw.bundle_e_sqlite3`, WAL mode | LiteDB, JSON files | Millions of rows, indexed queries for tree paging and views, transactional journal, single file, tooling for support. |
| Copy engine | **Own copy engine in-process** (`CreateFileW` with backup semantics → `FileStream`, temp file + rename, timestamps preserved, no ACL copy), parallel workers. **Robocopy is not the primary engine.** | Robocopy as backend | See §6. Robocopy remains available as an optional, switch-locked *bulk accelerator* behind the same interface, off by default in v0.1. |
| Registry reading | **Offline hive parser** (Eric Zimmerman's `Registry` NuGet package, MIT, managed, 2026.x releases target net10) for `NTUSER.DAT` and `SOFTWARE` discovery only | `RegLoadKey` / `RegLoadAppKey` | Loading a hive mounts it into the live registry and writes to the hive and its `.LOG1/.LOG2` transaction logs (dirty flag); it violates the read-only invariant. The offline parser reads the file (and can replay logs) without touching it. Fallback if the package proves unsuitable: a minimal in-house REGF reader (documented format, ~400 lines). |
| MVVM | `CommunityToolkit.Mvvm` | Prism, none | Source-generated observables and commands; small. |
| Logging | `Microsoft.Extensions.Logging` to a rolling text file in the session folder, with a redaction sink | Serilog | Fewer dependencies; redaction sink is custom anyway. |
| Hashing | `System.Security.Cryptography.SHA256` (hardware-accelerated), XXH3 not needed | | SHA-256 is fast enough for the sampled and sensitive-item verification. |
| Parsing helpers | `System.Text.Json` (browser JSON), `Microsoft.Data.Sqlite` (browser/Anki SQLite, opened read-only via immutable URI), `System.Xml.Linq` with DTD prohibited (Syncthing), `K4os.Compression.LZ4` (Firefox mozLz4), in-house SNSS reader (Chromium sessions) | | All read-only; browser SQLite files are copied to the session temp folder before opening so that `-wal`/`-shm` side files are never created next to the source. |
| Tests | xUnit + FluentAssertions; integration fixtures generated by `tools/FixtureGen`; UI smoke tests with FlaUI | | |
| Packaging/CI | GitHub Actions on `windows-latest`: build, test, publish x64/arm64, attach to release; SHA-256 checksums in release notes; code signing via SignPath.io or Azure Trusted Signing when available | | Unsigned elevated EXEs trigger SmartScreen; document this in README until signing is set up. |

### Not chosen

- **MFT direct reading** for scan speed: a plain enumeration of a 782k-file profile completed in 18 s on the reference machine. MFT parsing adds a volume-level dependency and risk for no v0.1 gain.
- **LibGit2Sharp** for repo inspection: native binary, single-file extraction issues, and it would need to be kept in read-only mode carefully. V0.1 reads `.git` metadata itself for discovery and shells out to `git.exe` (if present) for status, with write-suppressing flags.
- **Symlink recreation, VSS snapshots, hard-link restore**: not needed; source is offline.

## 2. Process and threading model

```
┌───────────────────────── WinOldRecovery.exe (elevated) ─────────────────────────┐
│ UI thread (WPF)            │ Engine host (background)                            │
│  Views ⇄ ViewModels        │  ScanService ── FileSystemWalker (1 thread/profile)  │
│  progress via IProgress<T> │  ClassifierPipeline (post-scan, SQL + rules)         │
│  tree pages via queries    │  RecipeRegistry (Detect/Plan/Execute/Verify)         │
│                            │  PlanBuilder, PreflightChecker                       │
│                            │  RestoreRunner ── CopyEngine (N workers)             │
│                            │  Verifier (hash workers)                             │
│                            │  PurgeExecutor (cleanmgr or manual deleter)          │
│ SessionDb (SQLite, WAL) ◄──┴── single writer connection + read connections        │
│ Child processes: robocopy.exe (opt), git.exe, wsl.exe, cleanmgr.exe, explorer.exe │
└─────────────────────────────────────────────────────────────────────────────────┘
```

- One session = one SQLite file at `%LOCALAPPDATA%\WinOldRecovery\sessions\<yyyy-MM-dd_HHmm>\session.db` plus `log.txt` and exports. The state DB is never placed on the source volume's `Windows.old` and never inside a destination the plan writes to.
- All engine work runs on the thread pool with `CancellationToken`s; the UI only issues commands and observes progress. No engine code touches WPF types.
- SQLite: one writer connection (serialized through a channel), many readers. Batched inserts (5,000 rows per transaction) during scan.

## 4. Domain model

```csharp
enum NodeKind { File, Directory, Junction, Symlink, MountPoint, CloudPlaceholder, Unknown }
enum Decision { Undecided, Restore, LeaveBehind }
enum DecisionSource { Inherited, SuggestedDefault, User }
enum Problem { None, AccessDenied, EfsEncrypted, CloudOnly, LongPath, InvalidDestName, ZeroByteStub }

record Node(long Id, long? ParentId, int ProfileId, string Name, string RelPath, NodeKind Kind,
            long Size, long AggSize, int AggFiles, DateTime MTime, FileAttributes Attrs,
            Problem Problem, bool Sensitive);

record Badge(long NodeId, string Kind, string Detail);           // "KeePass", "Regeneratable:node_modules", "GitRepo:unpushed"
record DecisionRow(long NodeId, Decision Decision, DecisionSource Source, DateTime At);
record Card(int Id, string RecipeId, int ProfileId, string Title, string Json);   // recipe-owned view model data
record Component(int CardId, string Key, Decision Decision, bool Fixed, string FixedReason);
record PlanItem(long Id, int JobId, PlanOp Op, string SourcePath, string DestPath, long Bytes,
                ConflictPolicy Conflict, bool OverwriteApproved, string RecipeId);
enum PlanOp { CopyFile, CopyTree, RecipeStep }
record JournalEntry(long PlanItemId, JournalState State, DateTime At, string Error);
enum JournalState { Pending, Started, Completed, Failed, Skipped, Paused }
record VerifyResult(long PlanItemId, VerifyLevel Level, bool Ok, string Detail);
```

Effective decision of a node = its own `User` decision if present, else nearest ancestor's `User` decision, else its own `SuggestedDefault`, else `Undecided`. Stored explicitly per node only when set; effective values are computed in SQL with a materialized `eff_decision` column refreshed on change for the affected subtree (bounded by the subtree size, done off-thread).

## 5. Scan and classify

### 5.1 Walker

- Input: source root, list of profile directories (`<root>\Users\*` minus `Default`, `Default User`, `All Users`, `Public` is treated as a profile named "Public (shared)").
- Uses `System.IO.Enumeration.FileSystemEnumerator<T>` with `EnumerationOptions { RecurseSubdirectories = false, AttributesToSkip = 0, IgnoreInaccessible = false, ReturnSpecialDirectories = false, BufferSize = 64 * 1024 }`, recursing manually with an explicit stack. (Note: the default `AttributesToSkip` is `Hidden | System` and the built-in recursion does **not** skip reparse points; manual recursion is what keeps junctions from being followed.) The enumerator reads name, size, times, and attributes straight from the directory buffer with no per-file syscall, and it opens directories with backup semantics, so deny-ACL folders list once `SeBackupPrivilege` is enabled. The rules:
  - reparse points (`FileAttributes.ReparsePoint`) are recorded as leaf nodes with their reparse tag (`FILE_ATTRIBUTE_TAG_INFO`) and target (`FSCTL_GET_REPARSE_POINT`, read-only) and **never descended**;
  - cloud placeholder attributes (`0x00400000 RECALL_ON_DATA_ACCESS`, `0x00040000 RECALL_ON_OPEN`, `0x1000 OFFLINE`) mark `CloudPlaceholder`; the file is never opened;
  - `Encrypted` attribute marks `EfsEncrypted`;
  - `UnauthorizedAccessException` on a directory records `AccessDenied` for that node and continues;
  - paths are built with the `\\?\` prefix once at the root, so lengths beyond 260 characters are not an issue for the runtime (.NET Core handles extended-length paths regardless of the `LongPathsEnabled` policy; the `LongPath` problem badge is informational for Explorer and for apps that will open the restored file).
- Emits nodes in batches to the DB writer. Aggregates (`AggSize`, `AggFiles`) are computed post-order in the walker so no second pass is needed.
- Performance target: ≥ 30,000 entries/s on NVMe (the reference profile scanned in under 30 s with `robocopy /L`; the walker should be within 2× of that). Progress reports every 250 ms.
- Optional hashing pass (files < 64 MB) is a separate stage so the initial tree appears fast.

### 5.2 Classifier pipeline (order matters)

1. **Structural**: profile roots, standard folders (by name and by old `NTUSER.DAT` "User Shell Folders" values, parsed offline), AppData subtrees, `Packages`.
2. **Recipe detectors** (each `IRecipe.Detect(profile)` returns cards + node badges + sensitivity flags). Detectors are read-only and must complete in bounded time per profile (target < 5 s total; heavy work such as git status is deferred to an on-demand "Analyze" action with progress).
3. **High-value patterns** (extension and folder-name rules from `Recipes/HighValue.rules.json`): badges only.
4. **Regeneratable patterns** (`Regeneratable.rules.json`): badge with reason ("`node_modules` is recreated by `npm install`"); never a decision.
5. **Sensitivity**: rules from SAFETY_MODEL §5; sets `Sensitive`.
6. **Suggested defaults**: table-driven (PRODUCT_SPEC §7), writes `DecisionSource.SuggestedDefault` rows.

Rules files ship inside the EXE as embedded resources and are documented so contributors can add patterns without code.

## 6. Copy engine

Why not Robocopy as the primary engine:

- Robocopy operates on directory trees plus name filters, not on arbitrary per-file decision sets. Expressing "restore these 40,000 files but not those 300" requires many invocations or exclusion lists that grow with the tree.
- Its output is localized and meant for humans; progress and per-file results must be scraped from `/UNILOG` text. Exit codes are coarse bitmasks.
- It cannot do temp-file-then-rename, per-file journaling, or in-line hashing, which the safety model requires.
- It is a separate elevated process per job; cancellation and pause are process-level.

What the in-process engine does:

- Opens the source with `CreateFileW(GENERIC_READ, FILE_SHARE_READ|DELETE, OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_SEQUENTIAL_SCAN)` (backup privilege enabled), wraps in `FileStream`, refuses placeholder/EFS/reparse nodes up front.
- Writes to `<dest>\<name>.winold-partial` with `CREATE_NEW`; copies with 1 MiB buffers; sets last-write/creation times from the source; then `MoveFileExW(partial → final)` with `REPLACE_EXISTING` only when the plan item is `OverwriteApproved`, otherwise `CREATE_NEW` semantics (fail if exists → apply conflict policy: keep-both renames the final to `<name> (from Windows.old).<ext>`; skip records `Skipped`).
- Streams the SHA-256 of the bytes it writes when the item requires L2 verification, so verification of sensitive/recipe items costs no second read of the destination (the source hash is computed in the same pass; the destination is re-read only for the sampled subset).
- 8 parallel workers by default (configurable 1–32), ordered largest-directory-first to keep workers busy; directory creation is idempotent.
- Journals `Started`/`Completed`/`Failed` per file; on resume, `Completed` items are skipped, `Started` items have their partial file deleted (it is in the destination, not the source) and are re-copied.
- Maps `ERROR_DISK_FULL`, `ERROR_HANDLE_DISK_FULL` to a job-level `Paused(DiskFull)`; `ERROR_SHARING_VIOLATION` on the destination to a retry (3×, 2 s) then `Failed`.
- Never copies ACLs, owner, alternate data streams (ADS: not copied in v0.1; the `Zone.Identifier` stream is deliberately dropped), or reparse data.

Robocopy adapter (optional, v0.2 default off): fixed switch set `/E /COPY:DAT /DCOPY:DAT /XJ /B /R:1 /W:1 /NP /BYTES /UNILOG:<file> /MT:16 /XC /XN /XO` for whole-directory plan items only; forbidden switches are unrepresentable in the argument model; exit code ≥ 8 fails the item; the log is parsed for per-file failures. Kept behind `IRestoreCopier` so the UI and journal do not care.

## 7. Recipes

```csharp
interface IRecipe {
    string Id { get; }                        // "syncthing"
    DetectResult Detect(ProfileContext ctx);  // read-only: cards, components, badges
    PlanResult Plan(CardDecisions d, DestinationContext dest);   // pure; lists every write
    Task Execute(PlanResult plan, IJournal j, CancellationToken ct);  // writes only what Plan listed
    VerifyResult Verify(PlanResult plan);     // L3 semantic checks
    IReadOnlyList<Prerequisite> Prerequisites(PlanResult plan);  // e.g. "firefox.exe not running"
}
```

- Recipes get a `ProfileContext` with: old profile root (read-only handle factory), parsed old `NTUSER.DAT` accessor, destination profile root, destination user's `%APPDATA%`/`%LOCALAPPDATA%`, a temp folder in the session directory, and `SafeFs`.
- Recipes never call `File.*` directly; they use `SafeFs`, which enforces I1 and refuses source writes.
- Recipe outputs that are files (bookmarks HTML, tab lists, extension lists) go to `<session>\exports\<recipe>\` and are listed in the verify report.
- Detailed per-app logic lives in RECOVERY_RECIPES.md.

## 8. Plan, preflight, verify, purge

- **PlanBuilder** walks effective decisions: a `Restore` directory whose subtree has no overriding `LeaveBehind`/`Undecided` becomes one `CopyTree` item; otherwise it is expanded into per-child items. Cards contribute `RecipeStep` items via `Plan()`.
- **Preflight** (Preview): destination existence and conflicts (per item, computed with an enumeration of the destination subtree and a size/time comparison), free space per destination volume, containment checks (I13), running-process checks for recipe prerequisites (`Process.GetProcessesByName`), recipe input validation, invalid destination names (reserved names, trailing dots/spaces, characters), path-length warnings.
- **RestoreRunner** executes jobs sequentially (one job per top-level card/folder) with intra-job parallelism; recipe steps run after file steps of the same job.
- **Verifier** implements levels L0–L3 (SAFETY_MODEL §7); results are immutable rows.
- **PurgeExecutor**:
  - Preferred: set `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\VolumeCaches\Previous Installations\StateFlags0777 = 2` (the key exists on Windows 11 25H2 with `SetupPrevInst=1`), run `cleanmgr.exe /sagerun:777`, poll until the folder is gone or cleanmgr exits, then remove the `StateFlags0777` value. `cleanmgr /autoclean` (documented as deleting files left after an upgrade) is the alternative trigger if `/sagerun` misbehaves. This makes Windows delete Windows.old exactly as Disk Cleanup does.
  - Fallback (custom roots, non-system volumes, cleanmgr missing): enable `SeTakeOwnershipPrivilege`/`SeRestorePrivilege`, walk bottom-up without following reparse points, take ownership + grant Administrators on each object that denies deletion, delete; clear read-only attributes; report residue.
  - Both paths require a `PurgeToken` (SAFETY_MODEL I10).

## 9. UI architecture

- Views: `ScanView`, `DecideView` (Cards pane, Files pane, Detail pane), `PreviewView`, `RestoreView`, `VerifyView`, `PurgeView`, `LogView`, `HelpView`.
- **TreeListView**: a virtualized `ListView` bound to a flat `ObservableCollection<TreeRow>` where expansion inserts the children rows (loaded from SQLite, sorted, paged at 2,000 with a "Show all" row). This pattern keeps WPF responsive with a million nodes because only visible rows exist as UI elements and the collection holds only expanded rows.
- **SmartCard** control: a template that renders the six-question block, instance selector, component list with decision chips, and the four verbs; recipes provide the data, not XAML.
- Global "space budget" and "source integrity" indicators are bound to `SessionState`.
- All long-running commands are `AsyncRelayCommand`s with cancellation.

## 10. Configuration, logging, support bundle

- No settings file in v0.1 beyond the session DB; a few advanced knobs (worker count, hash threshold, strong verify) live in the Scan options and are recorded in the session.
- Logs: `log.txt` with structured lines, redaction applied at the sink (paths under sensitive nodes replaced by `<sensitive:nodeId>`; canary tests enforce this).
- "Create support bundle" zips `log.txt`, the verify report, and a schema-only + counts export of `session.db` (no paths of sensitive nodes). Users share it manually; nothing is uploaded.

## 11. Build and publish

- `dotnet publish -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true -p:PublishReadyToRun=true`.
- `app.manifest`: `requireAdministrator`, `longPathAware`, DPI-aware per-monitor v2, Windows 10/11 compatibility GUIDs.
- Version stamped from git tag; About dialog shows version, commit, build date, and the trademark disclaimer.
- Minimum OS: Windows 10 1809 (x64) / Windows 11; the tool refuses to run on Windows 8.1 or earlier.
